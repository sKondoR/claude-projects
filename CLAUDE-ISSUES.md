# Учёт задач

Этот блок — общие правила учёта задач для всех проектов. Приложение Claude Projects обновляет его из эталона `_claude-projects/rules/issues-rules.md`. Не правь блок в проекте: правку внеси в эталон. Правила конкретного проекта лежат в `CLAUDE-ISSUES-LOCAL.md` в корне проекта. Если правило проекта расходится с общим, действует правило проекта.

## Где лежат задачи

Открытые задачи лежат в `docs/issues/`, один файл на группу. Ключ группы — имя файла без `.md`.

| Файл | Что в нём |
| --- | --- |
| `issues.md` | Задачи к работе. |
| `security-issues.md` | Находки проверок безопасности: секреты, данные пользователей, доступы. |
| `architecture-issues.md` | Архитектурные долги и переделки. |
| `other-issues.md` | Задачи вне кода: кабинеты, контент, задачи владельца. |
| `backlog.md` | Задачи, которые пользователь отложил сам, перетащив на доске. |

Любой другой файл `*.md` в `docs/issues/` тоже группа и тоже столбец на доске. Первая строка файла — `# Название группы`.

Доска — приложение Claude Projects. Оно следит за файлами и показывает изменения сразу. Пользователь переносит задачу между группами перетаскиванием и закрывает её кнопкой «Сделано». Приложение само правит файлы, поэтому перед правкой файла задач перечитай его.

## Формат задачи

```markdown
## Тема (область)

### К3 · Суть задачи

**Приоритет:** Средняя · **Трудность:** Лёгкая · **Риск:** 1 · **Зависит от:** С2, Л1 · **Ждёт этапа:** 1 · **Уточнить у владельца** · **Найдено:** 2026-11-18, аудит

Что известно — абзацы и списки.

- Что сделать: …

**Вопрос владельцу:** Какой телефон оставить единым во всех карточках?
- +7 (981) 028-48-48, как на сайте (рекомендуем)
- +7 (924) 591-66-08, как в 2ГИС
```

- Задача — это заголовок `### <номер> · <суть>` и всё до следующего заголовка `##` или `###`. Текст раздела `##` до первой задачи — пояснение к разделу, доска его не показывает.
- Строка полей идёт сразу под заголовком. Поля разделены ` · ` и стоят в таком порядке:
  - **Приоритет** — насколько важно: Высокая, Средняя или Низкая.
  - **Трудность** — объём работы: Лёгкая (одно место, час-два), Средняя (несколько файлов, до полудня), Сложная (миграция данных или поиск причины без зацепок, день и больше).
  - **Риск** — кто проверяет изменение: 0, 1 или 2. Поле обязательно. Ставь его, когда записываешь задачу. Перед PR сверь риск с диффом и поправь его.
    - 2 — человек смотрит изменение сам: деньги, данные пользователей, секреты и доступы, выкладка, публикация от имени владельца, то, что ломает позиции в поиске, миграция, которая удаляет или переносит данные или блокирует запись.
    - 1 — человек читает сводку: другое поведение функций без денег и данных, обновления зависимостей, служебные скрипты.
    - 0 — хватает проверки ИИ: вёрстка, стили, тексты, документы.
    - Риск решает смысл изменения, а не имена файлов. Если сначала нужен ответ владельца, оценивай изменение, которое последует за ответом.
    - Изменённое ожидание в существующем тесте или удалённый тест поднимают риск на 1, но не выше 2.
  - **Зависит от** — номера задач, которые закрываются раньше этой. Поле есть, только когда зависимость есть.
  - **Ждёт этапа** — этап плана проекта, до которого задачу не начать. Поле есть, только когда задача ждёт этапа. Такая задача остаётся открытой в своей группе, её не переносят в `backlog.md`.
    - Ставь поле и тогда, когда выясняется, что код задачи появится только на следующем этапе. В «Что сделать» укажи, что делать на этом этапе.
    - Ветка может записать по такой задаче только ответ владельца или решение. Тогда после открытия PR сними с задачи отметку командой `clear`. Иначе на задаче останется «PR».
    - Когда начинается этап N, найди его задачи командой `grep -rn "Ждёт этапа:\*\* N" docs/issues` и сними с них поле.
  - **Уточнить у владельца** — пометка без значения: задачу не начать без решения или доступа от владельца. В проекте владелец может называться иначе, например «заказчик».
  - **Найдено** — дата и источник: аудит, ревью, обсуждение.
- Задача с пометкой «Уточнить у владельца» заканчивается вопросами.
  - Каждый вопрос — строка `**Вопрос владельцу:** …`. Пиши его без имён файлов и функций. Вопрос должен быть понятен без остального текста задачи.
  - Если ответ — выбор, варианты идут пунктами под вопросом. У рекомендуемого варианта в конце стоит `(рекомендуем)`, такой вариант один.
  - Ответ запиши в подробности задачи и убери отвеченный вопрос. Пометку сними, когда вопросов не осталось.
- Подробности в `security-issues.md`: пункты «Где», «Сценарий», «Исправить». В остальных группах: что известно и «Что сделать».
- Ссылки пиши относительными от `docs/issues/`.
- Номер — буква области и число. Число следующее после наибольшего с этой буквой во всех файлах `docs/issues/` и `docs/resolved/*-DONE.md`. Номер закреплён за задачей навсегда: при переносе и после закрытия он не меняется. Буквы областей — в правилах проекта.

## Запись

- Новую задачу дописывай в конец подходящего раздела `##` или новым разделом в конец файла группы. В `backlog.md` не пиши: туда задачи переносит пользователь. Задачу, отложенную до условия («когда вырастет нагрузка», «если понадобится»), пиши в обычную группу.
- Находки проверок безопасности записывай сразу.
- Остальные задачи записывай только с согласия пользователя. Если после работы остались нерешённые задачи, в конце спроси разрешение их записать.

## Закрытие

Когда задача сделана, в том же изменении перенеси её блок целиком в конец файла-двойника в `docs/resolved/`. Сразу под строку полей добавь одну строку:
- `**Сделано:** <ДД.ММ.ГГГГ>, коммит, PR или что применено`;
- `**Не делаем:** причина`, если решили не делать;
- `**Отклонено:** причина или решение`, если задачу отклонили.

Файл-двойник — имя группы с `-DONE`: `security-issues.md` → `security-issues-DONE.md`. Задачи из `backlog.md` закрываются в `issues-DONE.md`. Ссылки на закрытую задачу из других документов веди на `-DONE`-файл.

Кнопка «Сделано» на доске делает то же самое и пишет `**Сделано:** <дата>, отмечено на доске`.

Начинай сообщение коммита с номера задачи: `С12: форма заявки`.

Если изменение идёт в основную ветку без PR, закрой задачу до push: в коммите с изменением или следующим коммитом. Хук git `pre-push` проверяет это. Он отменяет push в основную ветку, если сообщение коммита называет задачу, а в отправляемом коммите она ещё открыта. Если коммит задачу не закрывает, а только упоминает, отправь его командой `git push --no-verify`.

## Отметки на доске

Когда берёшь задачу в работу или меняешь этап работы, отметь это на доске:

```
node docs/issues/issues-status.mjs <номер> work <ветка>   — задача в работе
node docs/issues/issues-status.mjs <номер> simplify       — идёт /simplify
node docs/issues/issues-status.mjs <номер> review         — идёт code review
node docs/issues/issues-status.mjs <номер> pr <адрес PR>  — PR открыт
node docs/issues/issues-status.mjs <номер> clear          — снять отметку
```

Отметки `simplify` и `review` ставит хук доски, когда запускается `/simplify` или code review. Хук берёт задачу из последней отметки сессии, поэтому отметь `work` до начала работы.

Скрипт пишет `docs/issues/status.json`. Этот файл не добавляй в git. Скрипт ставит и обновляет приложение: не правь его в проекте.
